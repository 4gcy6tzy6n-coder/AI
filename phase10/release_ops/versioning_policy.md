# Versioning Policy - 版本管理策略

**版本**: v1.0  
**日期**: 2026-04-18  
**阶段**: Phase 10 - WP4: 发布与运维基线建立

## 1. 概述

本文档定义 Phase 10 的版本管理策略，确保系统从开发到发布的全生命周期可控、可追溯、可回滚。

## 2. 版本号规范

### 2.1 语义化版本 (Semantic Versioning)

格式: `MAJOR.MINOR.PATCH`

| 部分 | 含义 | 变更场景 |
|------|------|----------|
| MAJOR | 主版本 | 不兼容的 API 变更 |
| MINOR | 次版本 | 向后兼容的功能添加 |
| PATCH | 修订版本 | 向后兼容的问题修复 |

### 2.2 版本示例

```
1.0.0    # v1.0 正式发布
1.0.1    # v1.0 第一个补丁
1.1.0    # v1.1 功能更新
2.0.0    # v2.0 重大更新（不兼容）
```

### 2.3 预发布版本

格式: `MAJOR.MINOR.PATCH-PRERELEASE`

| 标识 | 含义 | 用途 |
|------|------|------|
| `-dev.N` | 开发版本 | 日常开发 |
| `-alpha.N` | 内测版本 | 功能验证 |
| `-beta.N` | 公测版本 | 用户测试 |
| `-rc.N` | 发布候选 | 发布前验证 |

### 2.4 版本示例（含预发布）

```
1.0.0-dev.1      # v1.0 开发版本 1
1.0.0-alpha.1    # v1.0 内测版本 1
1.0.0-beta.1     # v1.0 公测版本 1
1.0.0-rc.1       # v1.0 发布候选 1
1.0.0            # v1.0 正式发布
```

## 3. 分支策略

### 3.1 分支模型

```
main  (稳定分支，只接受合并)
  │
  ├── feature/xxx  (功能分支)
  │
  ├── release/v1.0  (发布分支)
  │
  └── hotfix/xxx  (热修复分支)
```

### 3.2 分支定义

#### main 分支

| 属性 | 规格 |
|------|------|
| 用途 | 稳定代码，随时可发布 |
| 保护 | 禁止直接推送 |
| 合并 | 只接受 PR，需审核 |
| 标签 | 每个发布版本打标签 |

#### feature/* 分支

| 属性 | 规格 |
|------|------|
| 命名 | `feature/{description}` |
| 来源 | 从 main 创建 |
| 目标 | 合并到 main |
| 生命周期 | 功能开发完成即删除 |

#### release/* 分支

| 属性 | 规格 |
|------|------|
| 命名 | `release/v{major}.{minor}` |
| 来源 | 从 main 创建 |
| 目标 | 合并回 main，并打标签 |
| 生命周期 | 发布后保留一段时间 |

#### hotfix/* 分支

| 属性 | 规格 |
|------|------|
| 命名 | `hotfix/{description}` |
| 来源 | 从最新 release 标签创建 |
| 目标 | 合并到 main 和 release |
| 生命周期 | 修复完成即删除 |

### 3.3 分支流程

```
日常开发:
main -> feature/xxx -> (PR) -> main

发布准备:
main -> release/v1.0 -> (测试) -> (PR) -> main (tag v1.0.0)

热修复:
main (tag v1.0.0) -> hotfix/xxx -> (PR) -> main (tag v1.0.1)
                              -> (cherry-pick) -> release/v1.0
```

## 4. 发布流程

### 4.1 发布类型

| 类型 | 频率 | 版本变更 | 示例 |
|------|------|----------|------|
| 日常发布 | 每周 | PATCH | 1.0.0 -> 1.0.1 |
| 功能发布 | 每月 | MINOR | 1.0.x -> 1.1.0 |
| 重大发布 | 每季 | MAJOR | 1.x.x -> 2.0.0 |
| 热修复 | 按需 | PATCH | 1.0.0 -> 1.0.1 |

### 4.2 标准发布流程

#### 阶段 1: 发布准备 (Release Preparation)

```
1. 从 main 创建 release/v{major}.{minor} 分支
2. 更新版本号到 {major}.{minor}.0-rc.1
3. 执行完整回归测试
4. 修复发现的问题
5. 更新 CHANGELOG
```

#### 阶段 2: 发布候选 (Release Candidate)

```
1. 标记为 rc.1, rc.2, ... 直到稳定
2. 执行验收测试
3. 文档更新完成
4. 发布检查清单全部通过
```

#### 阶段 3: 正式发布 (Official Release)

```
1. 更新版本号到 {major}.{minor}.0
2. 合并 release 分支到 main
3. 打标签 v{major}.{minor}.0
4. 创建 GitHub Release
5. 部署到生产环境
6. 删除 release 分支
```

### 4.3 热修复流程

```
1. 从最新标签创建 hotfix/{description} 分支
2. 修复问题
3. 更新版本号（PATCH + 1）
4. 执行冒烟测试
5. 合并到 main，打标签
6. 部署到生产环境
7. cherry-pick 到活跃的 release 分支
8. 删除 hotfix 分支
```

## 5. 版本兼容性

### 5.1 兼容性承诺

| 版本类型 | 兼容性保证 |
|----------|-----------|
| MAJOR | 不保证兼容，需迁移指南 |
| MINOR | 向后兼容，新功能可选 |
| PATCH | 完全兼容，只修复问题 |

### 5.2 API 兼容性

| 变更类型 | MINOR | MAJOR |
|----------|-------|-------|
| 添加新端点 | ✅ 允许 | ✅ 允许 |
| 添加可选参数 | ✅ 允许 | ✅ 允许 |
| 删除端点 | ❌ 不允许 | ✅ 允许 |
| 删除参数 | ❌ 不允许 | ✅ 允许 |
| 修改参数类型 | ❌ 不允许 | ✅ 允许 |
| 修改响应格式 | ❌ 不允许 | ✅ 允许 |

### 5.3 数据兼容性

| 变更类型 | 处理方式 |
|----------|----------|
| 新增字段 | 向后兼容，旧数据补默认值 |
| 删除字段 | 需迁移脚本，MAJOR 版本 |
| 修改字段类型 | 需迁移脚本，MAJOR 版本 |
| 修改字段含义 | 需迁移脚本，MAJOR 版本 |

## 6. 版本追踪

### 6.1 CHANGELOG 规范

使用 [Keep a Changelog](https://keepachangelog.com/) 格式：

```markdown
## [1.0.0] - 2026-04-18

### Added
- 新增功能 A
- 新增功能 B

### Changed
- 优化性能 C

### Fixed
- 修复问题 D

### Deprecated
- 废弃功能 E

### Removed
- 删除功能 F

### Security
- 修复安全漏洞 G
```

### 6.2 版本标签

每个发布版本必须打标签：

```bash
# 轻量标签（不推荐）
git tag v1.0.0

# 附注标签（推荐）
git tag -a v1.0.0 -m "Release version 1.0.0"

# 推送标签
git push origin v1.0.0
```

### 6.3 版本元数据

代码中应包含版本信息：

```python
# version.py
__version__ = "1.0.0"
__version_info__ = (1, 0, 0)
__release_date__ = "2026-04-18"
__commit_hash__ = "abc123"
```

## 7. 回滚策略

### 7.1 回滚触发条件

| 场景 | 响应时间 | 回滚目标 |
|------|----------|----------|
| 严重故障 | < 5 分钟 | 上一稳定版本 |
| 性能回退 | < 30 分钟 | 上一稳定版本 |
| 功能缺陷 | < 2 小时 | 上一稳定版本或热修复 |

### 7.2 回滚流程

```
1. 确认需要回滚
2. 通知相关团队
3. 执行回滚命令
4. 验证回滚成功
5. 创建事故报告
6. 分析问题原因
7. 准备修复版本
```

### 7.3 回滚命令示例

```bash
# 查看历史版本
git tag -l | sort -V

# 回滚到指定版本
git checkout v1.0.0

# 或创建回滚分支
git checkout -b rollback/v1.0.1 v1.0.0

# 部署回滚版本
./deploy.sh v1.0.0
```
