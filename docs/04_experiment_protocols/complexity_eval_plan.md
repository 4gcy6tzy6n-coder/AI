# 复杂度评估计划

**版本**: v0.7 Complexity & Generalization Validation  
**日期**: 2026-04-17  
**目标**: 量化比较本系统与传统 Transformer 路线的复杂度优势与代价边界

---

## 1. 评估目标

### 核心问题

本计划要回答：

1. **相对于传统 Transformer 路线，本系统到底赢在哪里？**
2. **在什么条件下，本系统的总成本是划算的？**
3. **检索与门控会增加哪些成本？这些成本是否可接受？**

### 比较对象

| 路线 | 描述 |
|------|------|
| **传统统一参数记忆** | 所有知识存储在模型参数中，通过训练更新 |
| **本系统（分层治理 + 外部知识 + 受控参数晋升）** | 知识分层存储，外部知识库，参数晋升受控 |

---

## 2. 评估维度

### 2.1 参数量成本

#### 指标定义

| 指标 | 定义 | 测量方法 |
|------|------|----------|
| 总参数量 | 模型中所有可训练参数的数量 | 统计模型参数 |
| 有效参数量 | 实际参与推理的参数数量 | 运行时统计 |
| 参数利用率 | 有效参数 / 总参数 | 计算比率 |

#### 预期结果

**传统路线**:
- 需要大量参数存储所有知识
- 参数利用率低（很多参数存储很少使用的知识）

**本系统**:
- 基础参数量较小（只存储核心能力）
- 知识存储在外部知识库
- 参数利用率高（按需加载）

### 2.2 显存占用

#### 指标定义

| 指标 | 定义 | 测量方法 |
|------|------|----------|
| 推理时显存 | 单次推理所需的显存 | 内存分析器 |
| 峰值显存 | 训练或批量推理时的峰值 | 内存分析器 |
| 知识库缓存显存 | 缓存常用知识所需的显存 | 统计缓存大小 |

#### 预期结果

**传统路线**:
- 推理时显存固定（与知识量无关）
- 但模型本身很大

**本系统**:
- 基础模型较小
- 但检索和缓存会增加显存波动
- 需要评估缓存策略的效率

### 2.3 内存占用

#### 指标定义

| 指标 | 定义 | 测量方法 |
|------|------|----------|
| 知识库内存 | 外部知识库占用的内存 | 统计存储大小 |
| 索引内存 | 检索索引占用的内存 | 统计索引大小 |
| 运行时内存 | 系统运行时总内存 | 内存分析器 |

### 2.4 检索开销

#### 指标定义

| 指标 | 定义 | 测量方法 |
|------|------|----------|
| 单次检索延迟 | 执行一次检索的时间 | 计时器 |
| 检索吞吐量 | 每秒可执行的检索次数 | 压力测试 |
| 检索准确率 | 检索到正确知识的比例 | 测试集评估 |

#### 预期结果

**传统路线**:
- 无检索开销
- 但所有知识都在参数中，推理时都要参与计算

**本系统**:
- 有检索开销
- 但只检索需要的知识，减少计算量
- 需要评估检索开销 vs 计算节省的权衡

### 2.5 长期知识更新成本

#### 指标定义

| 指标 | 定义 | 测量方法 |
|------|------|----------|
| 新知识注入时间 | 添加一条新知识所需时间 | 计时器 |
| 知识更新成本 | 更新已有知识所需资源 | 资源监控 |
| 知识验证成本 | 验证新知识正确性所需资源 | 资源监控 |

#### 预期结果

**传统路线**:
- 需要重新训练或微调
- 成本高，可能影响其他知识

**本系统**:
- 直接写入知识库
- 通过治理链验证
- 成本低，不影响其他知识

### 2.6 错误修复成本

#### 指标定义

| 指标 | 定义 | 测量方法 |
|------|------|----------|
| 错误识别时间 | 发现错误所需时间 | 测试集评估 |
| 错误修复时间 | 修复错误所需时间 | 计时器 |
| 修复副作用 | 修复错误对其他知识的影响 | 回归测试 |

#### 预期结果

**传统路线**:
- 错误隐藏在参数中，难以定位
- 修复需要重新训练
- 可能引入新的错误

**本系统**:
- 错误在知识库中可见
- 可直接修改或隔离
- 通过治理链验证修复

class ComplexityProfiler:
    def measure_param_cost(self, model):
        """测量参数成本"""
        total_params = count_parameters(model)
        effective_params = measure_active_params(model, test_data)
        utilization = effective_params / total_params
        return {
            "total": total_params,
            "effective": effective_params,
            "utilization": utilization
        }
    
    def measure_memory_cost(self, model, knowledge_base):
        """测量内存成本"""
        model_memory = get_model_memory(model)
        kb_memory = get_kb_memory(knowledge_base)
        index_memory = get_index_memory(knowledge_base)
        return {
            "model": model_memory,
            "knowledge_base": kb_memory,
            "index": index_memory,
            "total": model_memory + kb_memory + index_memory
        }
    
    def measure_retrieval_cost(self, queries):
        """测量检索成本"""
        latencies = []
        for query in queries:
            start = time()
            result = retrieve(query)
            latencies.append(time() - start)
        return {
            "avg_latency": mean(latencies),
            "p99_latency": percentile(latencies, 99),
            "throughput": len(queries) / sum(latencies)
        }

## 4. 预期结果与分析框架

### 4.1 系统优势（预期）

| 优势 | 说明 | 量化指标 |
|------|------|----------|
| **参数效率** | 用更少的参数存储更多知识 | 参数利用率提升 X% |
| **知识更新效率** | 新知识注入更快 | 更新时间减少 Y% |
| **错误可修复性** | 错误更容易定位和修复 | 修复时间减少 Z% |
| **可解释性** | 知识来源可追溯 | 透明度提升 |

### 4.2 系统代价（预期）

| 代价 | 说明 | 量化指标 |
|------|------|----------|
| **检索延迟** | 每次推理需要检索 | 延迟增加 X ms |
| **内存开销** | 知识库和索引占用内存 | 内存增加 Y MB |
| **系统复杂度** | 更多组件需要维护 | 代码量增加 Z% |

### 4.3 划算条件

本系统在以下条件下更划算：

1. **知识量大且动态更新频繁**：知识更新成本节省 > 检索开销
2. **错误修复需求高**：错误修复成本节省 > 系统复杂度成本
3. **可解释性要求高**：透明度提升的价值 > 检索延迟成本
4. **资源受限场景**：参数效率提升的价值 > 内存开销成本
